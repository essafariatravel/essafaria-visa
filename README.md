# ESSAFARIA VISA OS

**B2B visa operations platform for ESSAFARIA TRAVEL** — a database-driven, admin-configurable foundation for agency management, visa catalog configuration and the public website.

> **Core principle:** *no code change required for normal business configuration.* Countries, visa types, requirements, statuses, priorities, fees, currencies, document types, communication templates, branding, logos, colors, homepage content, navigation, footer and legal text all live in the database and are managed from the Admin Control Panel.

---

## Architecture (three layers)

```
LAYER 3 — EXPERIENCE     Admin Control Panel · Agency Portal · Public Website (CMS-rendered)
LAYER 2 — BUSINESS CONFIG countries, visa types/categories/requirements, statuses,
                          priorities, currencies, fees, templates, branding,
                          homepage sections, navigation, legal pages, site settings
LAYER 1 — PLATFORM CORE  PostgreSQL (Drizzle ORM + SQL migrations), users & sessions,
                          RBAC capabilities, agency tenancy, audit log, media storage
```

Layers 2 and 3 are data; layer 1 never assumes what they contain. New configuration entities are added by extending the registry in `src/lib/crud.ts` + `src/app/admin/entity-ui.ts` — the table, form, audit and cache invalidation come for free.

## Stack

| Concern | Choice | Why |
|---|---|---|
| Web | Next.js 14 (App Router), React 18, TypeScript strict | Server components read the DB directly; mutations via server actions |
| Database | **PostgreSQL** via Drizzle ORM | The canonical datastore. `pgTable` schema, real constraints/FKs/enums |
| Driver | `postgres` (production) / `PGlite` (sandbox/tests) | PGlite is *the same Postgres engine* embedded — used only because this sandbox has no Postgres server. **Not a production dependency** |
| Migrations | `drizzle/` SQL files, generated by drizzle-kit | Identical SQL applies to both drivers |
| Auth | DB-backed sessions (scrypt via node:crypto, sha256-hashed tokens in httpOnly cookies) | No third-party IdP needed for the foundation |
| Authorization | Capability matrix (`src/lib/rbac.ts`) — checked server-side on every mutation | UI hiding is UX, never security |
| Media | Storage-provider abstraction (`src/lib/storage.ts`) — local disk today, S3-compatible tomorrow | Never stores binaries in Postgres |
| Validation | Zod — one schema set shared by server actions & services | Structured, never raw HTML |

## Production: managed PostgreSQL

The production driver is not a theory here: the whole suite, the concurrency check and the
HTTP verification have been run against a real PostgreSQL server (18.4), and the deployment
artifacts are in the repo.

```bash
DATABASE_URL=postgresql://... npm run db:migrate
DATABASE_URL=postgresql://... npm run db:seed   # only for a fresh environment
DATABASE_URL=postgresql://... npm run deploy:check   # preflight: config, migrations, storage, providers
npm run build && npm start
```

`DATABASE_URL` being set resolves `dbMode=postgres` automatically (`src/lib/env.ts`).
Run the same evidence the release depends on:

```bash
npm run test:postgres        # the full suite against a server, one database per test file
npm run verify:concurrency   # 24-way creates, 20-way charges, 6 dispatchers, 10 uploads → 9 invariants
```

For a container host: `cp .env.example .env`, edit the three required values, then
`docker compose up -d --build`. The image preflights, migrates and starts on every boot;
CI (`ci/github-actions/ci.yml`, copy it into `.github/workflows/` to enable) runs the suite on PostgreSQL 16 and 18 and builds the image.
`DEPLOYMENT.md` §8 is the go-live checklist and §10 the release path.

## What the Admin Control Panel configures (no code)

Agencies (create/deactivate/suspend + member assignment) · Users & roles · Countries · Visa categories · Visa types (processing time, eligibility, featured flag) · Per-type requirement checklists (required/optional, instructions, min validity, order) · Document types (extensions, max size) · Application statuses (label, color, terminal flag, order — renames preserve history) · Priorities (+ surcharge %) · Currencies · Effective-dated fees (integer cents, per currency & fee type) · Communication templates (whitelisted `{{variables}}` only) · Branding (logos, favicon, 5 colors, button style — flows to every surface as CSS tokens) · Homepage section builder (order, activate, draft→publish) · Navigation (header/footer, system items protected) · Legal pages (structured blocks) · Site settings (typed, per-key validated) · Media library · Audit log viewer.

## Safety model

- **History integrity (§23):** stable UUIDs + active flags; deletions of referenced rows are blocked by `ON DELETE RESTRICT`; renames never break links.
- **Tenant isolation (§27):** agency scope is derived from the session's memberships **server-side only**. URLs carry no agency identifiers for portal reads.
- **Audit (§24):** every config mutation writes `audit_logs` (actor, action, entity, before/after diff) **inside the same transaction**.
- **Input safety (§34):** hex-color / code-format / href validation; template placeholders whitelist-checked; SVG rejected on upload (magic-bytes sniffed); content stored as structured blocks — never rendered as raw HTML.
- **Fallbacks (§32):** missing branding/logo/sections degrade to safe defaults and log loudly — the public site cannot 500 on empty configuration.

```bash

```

### One writer per PGlite directory

`DATABASE_MODE=pglite` runs Postgres **inside the process**, so the app and a CLI job (`db:migrate`, `outbox:drain`, `automation:run`) cannot share `.data/pgdata`. `src/lib/pglite-writer-lock.ts` makes that explicit: the second opener is refused with the pid to stop, instead of both processes corrupting the cluster. Against real Postgres (`DATABASE_URL`) the guard does not apply — many concurrent writers are normal there. `ALLOW_PGLITE_MULTI_PROCESS=1` overrides for anyone who really knows why.

### Scheduled jobs

```bash
npm run outbox:drain       # deliver queued email intents (safe to re-run: claims + idempotency keys)
npm run automation:run     # due tasks: expiry sweep, document reminders, digest, retry queue...
```

Both exit non-zero when something failed, so cron/CI can alert. Under Postgres, run them on a timer; under PGlite, run them with the web process stopped.
